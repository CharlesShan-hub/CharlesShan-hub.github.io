RFC 5 — DEL（Decode-Encode Language，解码-编码语言）· Jeff Rulifson

一句话定位：RFC 1 里那句"发明一种叫 DEL 的语言"的完整兑现——1969 年 6 月，Rulifson 把 DEL 从概念变成了完整的形式语法规范。这是人类第一份"远程下发前端代码、本地编译执行"的正式语言规格，比 Web 浏览器早了整整 25 年。

〇、背景：一条从 1968 年 10 月走来的路

RFC 5 开头有一节 FORWARD（前言），把 DEL 的来龙去脉记得清清楚楚：

  • 1968 年 10 月 25–26 日，首次 NWG 会议在 SRI 召开。会前大家就达成共识："跨网络运行交互式程序"将是第一个要面对的难题。 参会者：Andrews、Baray、Carr、Crocker、Rulifson、Stoughton。
  • 1968 年 11 月 18 日，Crocker 到 SRI 找 Rulifson，讨论后把协程（co-routine）纳入了 DEL。
  • 1968 年 12 月 12 日，Stoughton 又到 SRI 找 Rulifson，决定次年 1 月底在 Utah 开全体会。
  • 1969 年 2 月 13 日，在剑桥的 BBN NET 会议上首次公开发表。

所以 RFC 5 不是一个人拍脑袋的产物——它经过了三次面对面会议、历时 4 个月的演进，是 NWG 第一个"走完完整讨论流程"的正式成果。

一、内容细读

1. DEL 是干嘛的（ABSTRACT）

DEL 是一门机器无关语言，专门干两件事： ① 从交互式控制台接收输入码、给出即时反馈、把结果打包成消息包发到网络； ② 从另一台计算机接收消息包、解包、构建显示信息树、把信息呈现给用户。

一句话：DEL = 网络时代的第一门"前端语言"。 它把"人机交互"这件事完全独立成一个可编程、可下发、可在任意机器上编译的模块。

2. NST：三个使用层级

NST（Network Standard Translator，网络标准翻译器）是一套标准库，规定了 DEL 程序在不同场景下的工作方式：

层级 工作方式 场景
最低 直通模式（NST 默认不动作），DEL 程序退化成"消息组装发送器" 用户端和服务器端格式恰好兼容时
中级 用回显表（echo tables）给 TTY 做回显：本地回显字符、翻译成服务器字符集、打包、遇到断行符就发送；收消息时再翻译回来打印 远程登录一个普通 TTY
最高 由 DEL 程序在用户端处理所有即时反馈（像一个复杂的回显表），只在合适的按钮事件发生时发消息给服务器、接收显示更新 大型显示系统（图形终端远程操控）

注意中级那个"遇到断行符（break characters）就发送"——这就是你之前认出的「行缓冲」在 1969 年网络协议里的版本：攒到语义边界再发，而不是每敲一个字符就发。

第 3 个层级还点破了一个关键问题：大交互系统如果每个按钮状态变化都激活 TSS 里的用户程序，"会轻易地同时压垮两个系统"（服务器一个 + 网络链路一个）。所以必须让 DEL 在用户端本地扛下即时反馈——这就是 RFC 1 里"琐碎响应本地化"思想的工程化论证。

3. 通用硬件表示法（Universal Hardware Representation）：归一化坐标

为了让"任何控制台 ↔ 任何主机"只需要最小数量的翻译器，DEL 定义了一套通用硬件表示法：

显示被想象成一个正方形，中点是 (0,0)，两个轴的取值范围都是 -1 到 1。无论某台显示器的光栅点密度是多少，一个点都可以用这套坐标指定到任意精度。

-1 到 1 的归一化坐标——这就是 1969 年的"设备无关渲染"。今天你写 SVG 的 viewBox、CSS 的相对单位、游戏引擎的 NDC（归一化设备坐标），都是它的直系后代。

4. REP：符号程序下发（用户视角的完整例子）

RFC 5 用 NLS 举了个端到端例子：Utah 的用户想跑 SRI 的 NLS。

① Utah 用户正常登录 AHI 系统，想跑 NLS
② Utah 系统向 NLS 请求一个"符号程序" → NLS 发来 REP（Remote Encode Program，远程编码程序）
   ——注意：发的是 DEL 写的符号源码，不是二进制
③ Utah 收到后本地编译 + 加载，和标准库（NST）一起运行
④ 之后 Utah 控制台的所有输入先经过本地的 NLS REP：
   处理、解析、打包、翻译……攒到合适状态才向 940 发起传输
   （传过去的 bits 是 940 能接受的格式，甚至可以是标准格式，这样 NLS 不用区分 Utah 和其他用户）

这一步直接把 RFC 1 的"前端源码下载"变成了可执行的产品流程：源码下发 → 本地编译 → 本地处理即时反馈 → 只在语义边界发远端。

5. NST 的优点（ADVANTAGES OF NST）

  • 每个节点只要给每个子系统写一个符号程序——就是发给用户的那份 DEL 源码，把通用硬件表示映射到自家位格式。这是"让控制台发挥到极致"时最小的编程量。
  • 编码翻译在用户端运行，可以充分利用用户本地控制台硬件；增减硬件功能不需要主机更新翻译表。
  • 主机加了新功能，改一下符号编码程序，用户端重新编译就自动获得新功能——这就是今天的"前后端约定接口，前端自动更新"的 1969 版。
  • 符号传输的另一个好处：每个站点可以按自己的方式翻译、生成最适合自家机器的机器码，运行更快、代码更紧凑。
  • 还能在用户监控系统和主机的 DEL 程序之间插入额外的符号程序，解决"控制台扩展"（比如适配不寻常的键和按钮）问题。

文中有句话特别可爱：

"也许有一天可以通过程序组合实现（等 Crocker 告诉我们怎么做？？）"

括号里的 "when Crocker tells us how??" 是 Rulifson 的吐槽——RFC 文化里，不懂就问、问得理直气壮。

6. DEL 语法：一门完整的语言

RFC 5 的后半部分是 DEL 的完整形式语法（用当时标准的 BNF 类元记法写成），包含：

语法节 内容
PROGRAMS（程序） 程序 = 元文件 + 声明 + 过程 + "FINISH"；区分 FUNCTION（返回值）和 PROCEDURE（无返回值）；CO-ROUTINE（协程）无名字无参数，通过 PIPE 声明初始入口
DECLARATIONS（声明） 数类型（REAL/INTEGER + CONSTANT）、结构化类型（tree 树 / pointer 指针 / buffer 缓冲）、标签、PIPE（成对 id）
ARITHMETIC（算术） IF-THEN-ELSE 表达式、位运算（/\=异或，↑=取模）、一元负号；位运算符优先级相同，必须用括号分组（没有标准约定）
CONJUNCTIVE（逻辑表达式） AND/OR/NOT；特别设计了"短路求值"——左半为假就不需要求值右半
SEMI-TREE（半树操作） set pointer / insert as left-right brother / first-last daughter / replace / delete——树结构操作；"多余的括号导致线性子分类，就像 LISP 一样"
FLOW AND CONTROL GO TO、CALL/RETURN、STUFF...IN（往 PIPE 塞值）/ FETCH（取协程值）、WHILE/UNTIL/FOR（FOR 的循环变量只读）、ITHCASE/CASE
I/O start/append/send message、get message byte、message length
DISPLAY BUFFERS（显示缓冲） start buffer / append（character/string/vector/position beam to/curve）/ intensity/width/blink/italics 参数、establish buffername
LOGICAL SCREEN 屏幕=正方形，坐标 -1..1；PREG 位置寄存器 = 三元组 （r 是从 x 轴逆时针的弧度旋转）；INTENSITY 0..1 对数亮度；字符框尺寸；闪烁位
逻辑输入设备 Wand（魔杖）、Joy Stick（操纵杆）、Keyboard（键盘）、Buttons（按钮）、Light Pens（光笔）、Mice（鼠标）

注意看最后一行——1969 年 6 月的文档里，鼠标就作为标准逻辑输入设备列进语言规范了。 而 Engelbart 的"所有演示之母"是 1968 年 12 月。Rulifson 和 Engelbart 在同一栋楼里工作，鼠标在这份语言规范里出现毫不意外。

还有几处 Rulifson 的真情流露：

"Strings are a big problem? Rulifson also wants to get rid of real numbers!!" （字符串是个大麻烦？Rulifson 还想把实数也干掉！！）

— 语言设计者的烦恼，57 年后的今天依然如故。

二、🔷 本质升华

  • 「人类发明的实现」：PIPE、FETCH、STUFF...IN、ITHCASE、半树、-1..1 坐标——这套具体语法和词汇全是 1969 年 Rulifson 们的选择。如果换一个人设计，会变成完全不同的语言（后来 JavaScript、WASM 各有各的语法）。DEL 的语法细节没有一个活到今天，但它的骨架全部活了下来。
  • 「先于人类存在的规律」： ① 计算迁移律（你在 RFC 1 已经认出的那条）——REP 源码下发 + 本地编译 + 本地即时反馈，是这条律第一次被写成完整可执行的工程规格；"遇到断行符才发送"是它的缓冲形态。 ② 设备抽象律（新增）：-1..1 归一化坐标 + 逻辑输入设备清单，本质是"在任何具体硬件之上建立一层纯逻辑的设备模型"。硬件千变万化，逻辑模型只有一个——这样"任意终端 ↔ 任意主机"就只需要翻译器和逻辑模型之间的一层映射，而不是每对设备都写一个翻译器（O(n²) → O(n)）。这就是 SVG viewBox、游戏引擎抽象层、打印机 PostScript、Linux 输入子系统（evdev）背后同一条规律：抽象层把 M×N 的问题变成 M+N。 ③ 符号源码作为分发格式：发源码而不是二进制——因为源码可以在每台机器上"针对性编译"（更快更紧凑）。这条选择在 1969 年是性能优化，在 2026 年变成了开放性与可审计性（开源、源码映射）。同一条决策，时代赋予它新的含义。
  • 后世重现：REP 源码下发 → JS + React 前端；NST 三级 → HTTP + SSR + SPA 的演进路线；归一化坐标 → SVG viewBox / 游戏 NDC；显示缓冲 + 半树 → HTML DOM + 虚拟 DOM / 保留模式渲染；协程 PIPE/FETCH → Go goroutine + channel（迟了整整 40 年）；逻辑输入设备 → DOM 的 input event / PointerEvent；"等 Crocker 告诉我们怎么做" → GitHub issue 的日常。DEL 语言本身死了，但它的每一个器官都投胎成了今天前端世界的骨干。

三、亮点速览

  1. 机器无关的"前端语言"完整语法——比任何 Web 技术早 25 年。
  2. -1..1 归一化坐标——设备无关渲染的原始设计。
  3. 符号源码下发 + 本地编译——"发源码不发二进制"的性能与开放双赢。
  4. 协程（co-routine）进入语言设计——1968 年 11 月加进 DEL，Go 的 goroutine 晚了 40 年。
  5. 逻辑输入设备清单里赫然列着 Mice（鼠标）——1969 年。
  6. "等 Crocker 告诉我们怎么做？？"——RFC 文化非正式性的完美标本。

四、成败与后续

  • 失败的：DEL 语言本身没有大规模铺开。原因很实在——每个站点都要为 DEL 写编译器（文档里自己也承认"各站点写各自平台的 DEL 编译器"），四台异构主机的编译器开发成本远超收益；而 1970 年 telnet（RFC 15/97）用"直接模拟 TTY"的简单方案解决了 90% 的需求，剩下的图形需求等了 15 年才由 X11 接棒。
  • 成功的（思想投胎）：
  • X11（1984）：服务器下发绘图原语、客户端本地渲染——DEL 的图形路径直系后代；
  • JavaScript + 浏览器（1995）：把交互代码下载到用户端执行——DEL 的 REP 直系后代；
  • React/Vue + WASM（2015+）：本地 re-render + 虚拟 DOM——半树与显示缓冲的现代形态；
  • 协程思想：从 DEL 的 PIPE/FETCH 一路经 Simula/Modula 到 goroutine。
  • 历史彩蛋：RFC 5 文首有一行 :DEL, 02/06/69 1010:58 JFR ... dual transmission?——Rulifson 直接在文档标题下写了一句 DEL 代码当开场白，最后还跟了个问题 "dual transmission?"。论文标题页写代码+吐槽，这就是 1969 年的文档风格。
