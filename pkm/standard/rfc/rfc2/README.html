RFC 2 — Host Software（主机软件）· Bill Duvall

一句话定位：RFC 1 的"姊妹篇"——同一个议题（主机软件），Crocker 从 UCLA 写了第 1 号，Duvall 从 SRI 独立写了第 2 号。如果说 RFC 1 是"设计宣言"，RFC 2 就是"实现者的施工图纸"：编号条款、状态机、错误处理、系统调用清单，全是干货。

〇、背景：为什么同一主题会有两份文档？

1969 年 4 月，网络工作组（NWG）是一个松散、开放的小组（RFC 3 里明确写了 "Membership is not closed"——成员资格不封闭）。四个站点各自选代表，分头想问题，然后再把想法寄到 UCLA 汇总编号。所以：

  • RFC 1（Crocker，4 月 7 日）：从"我们要达成什么体验"出发，讲需求层次和 DEL 构想——设计师视角。
  • RFC 2（Duvall，4 月 10 日）：从"这个操作系统到底要怎么写"出发，把链路管理、错误处理、系统调用一条条列出来——实现者视角。

两人互相不知道对方在写什么（文档标题栏甚至都叫 HOST Software），结果却在关键决策上惊人地一致：链路 0 当控制、ID 小的让、端到端校验。这就是 1969 年的"并行开发"——没有 version control，靠邮件和面基对齐。

一、内容细读

1. 三种链路（LINKS）——比 RFC 1 更细的分层

RFC 1 只说了"0 号控制 + 31 条数据"。RFC 2 把"数据链路"进一步拆成了两种：

链路类型 数量限制 生命周期 用途 类比
控制链路（Control Link） 每对 HOST 只有 1 条（n 台主机 → 每个 HOST 有 n-1 条控制链路） 系统加载时建立，永远在 建立/断开用户链路、传递中断、监控通信 交换机总机
主链路（Primary Link） 每个用户对每个远端 HOST 至多 1 条 全局，直到显式关闭 像一台 TTY 直连远端，用于登录（走远端标准登录流程） 你的"专线"
辅助链路（Auxiliary Link） 任意数量 局部于某个子系统，离开即关闭 二进制或字符传输，用于传文件等 临时开的管道

注意两个细节： - "n-1 条控制链路"——你在 RFC 1 里观察到的「1 管理 + N-1 数据」结构，在这里再次出现，而且这次是文档里白纸黑字写出来的。 - 主链路像 TTY：1b1c 说"远端 HOST 把主链路当成一台通过数据电话拨进来的普通电传打字机用户"——RFC 1 里"远程使用要像 TTY"的目标，被 RFC 2 落实成了具体机制。

2. getlink 协议：建立链路的完整状态机

RFC 1 只画了流程图，RFC 2 把状态机写全了（第 2b1d 节）：

A 要连 B：
  ① A 从自己的分配表里挑一条没在用的链路
  ② A 通过链路 0 给 B 发「链路连接消息」
  ③ A 等待：B 的回应 / 超时
  ④ 收到 B 的回应，分三种情况：
     a. B 确认了这条链路 → 成功，返回链路号给调用者
     b. B 也在请求建这条链路（撞车了！）→ 冲突仲裁（见下）
     c. 其他消息 → 错误：A 发断开消息 + 进入 panic 例程
  ⑤ 超时没回应 → B 被视为出错：发断开消息 + 调 panic 例程

冲突仲裁规则（2b1d4b）——和 RFC 1 完全一致：如果 A 的 ID 比 B 大（Na > Nb），A 无视 B 的请求继续等；如果 A 的 ID 比 B 小（Na < Nb），A 成全 B 的请求、发确认、然后放弃自己的请求重新分配。ID 小的让。 一条确定规则，分布式解决冲突，不需要中心协调。

3. 折叠校验和（Folding Checksum）：异构机器的最大公约数

RFC 2 第 3 节把校验和算法定得比 RFC 1 更具体。最精彩的是字段长度：

字段长度 288 bits = lcm(24, 32, 36)

为什么是这三个数？因为四站主机字长不同： - UCLA 的 SDS Sigma 7：32 bit - SRI 的 SDS 940：24 bit - Utah 的 PDP-10：36 bit

288 是三种字长的最小公倍数——这样每台机器都能用自己最顺手的字长整数次对齐地切分字段，校验算法在每台机器上都是相对最优的。校验和本身取 8 bits（所有机器都方便处理的长度）。

这就是"标准化"最纯粹的形式：不是选一个赢家，而是找一个所有人都不吃亏的共同分母。 而校验和是顺序相关的（order dependent）——每算完一组字段，把结果循环移动再和下一组叠加（和 RFC 1 的"每 1152 bits 右旋一位"是同一家族的设计），专门对付"包顺序调换"这类 bug。

另外 3c 提供一种正验证模式：两个 HOST 可以约定所有消息都要确认，确认走控制链路发。

4. Monitor 功能与 Executive 原语：1969 年版的操作系统网络模块

  • Monitor（监控程序） = 操作系统核心。RFC 2 第 4 节规定了它要干的活：
  • 输入：从 IMP 收消息 → 校验 → 字符翻译（EBCDIC↔ASCII 这类，还没定，要跟 BB&N 商量）→ 解码头部 → 按源和链路号分发给正确接收者
  • 输出：建头部 → 字符翻译 → 算校验和 → 检查链路状态（上一条 RFNM 还没回来就等着） → 发给 IMP
  • 网络状态维护：维护其他 HOST 的状态表（IMP 挂了就算 HOST 挂了）、维护控制链路状态、响应状态查询、中断时主动通知其他 HOST 各链路/程序状态
  • Executive Primitives（执行原语） = 系统调用。第 5 节列了给用户程序用的 API：建立/杀死主链路、把控制 TTY 接到主链路、主链路 I/O、状态查询；辅助链路的建立（返回一个类似文件句柄的逻辑链路号）、I/O、杀死。还有个 Transparent I/O（透明传输）：不经过任何处理直接把缓冲交给 IMP，标注"主要用于网络调试"——这就是后来"raw socket"的祖先。

5. 初始联调（Initial Checkout）：从 DDT 到 DDT

第 6 节给出了第一个测试方案：先用模拟电话线模式跑，所有消息一次只发 1 个字符，链路对 Monitor 透明、由用户程序用特殊原语控制。测试程序就是两个不同 HOST 上的 DDT 到 DDT（DDT 是那个年代的调试器），旁边并行开一条电话线人肉对照。

二、🔷 本质升华

  • 「人类发明的实现」：288 bits、8 bits、三种链路的名字（Primary/Auxiliary/Control）、getlink 的五步流程——全是 1969 年工程师的选择。换成 128 位对齐、叫法改成 session/stream/control，一样成立。
  • 「先于人类存在的规律」：这里藏着好几条你已经在 RFC 1 里认出来的规律，RFC 2 是它们的制度化版本： ① 「1 管理 + N-1 数据」律——控制链路 n-1 条、主链路 1 条，白纸黑字写进了规格； ② 对称冲突仲裁律——"ID 小的让"被写成了 2b1d4b1 的 if-else 条款； ③ 大物拆分律 + 冗余指纹律——288 位分块 + 顺序相关折叠校验和； ④ 最小正交接口律——第 5 节那 8 个原语，就是最早的 POSIX socket API 胚胎。
  • 新增的一条观察——「共同分母律」：288 = lcm(24,32,36) 这个故事的本质是：当一群异构实体必须互操作时，最优策略不是选一个"标准赢家"，而是找一个所有人都不吃亏的最小公倍数作为公共接口。 这和 UNICODE 统一了各国编码、USB-C 统一了充电口、TCP/IP 统一了各厂商网络协议是同一件事——标准化 = 找最小公倍数，不是选最优解。
  • 后世重现：控制链路 → TCP 连接 + 会话层；主链路像 TTY → telnet/SSH 的虚拟终端模型；辅助链路 → FTP 数据通道 / QUIC 的多流；Transparent I/O → raw socket / AF_PACKET；Monitor 状态表 → 路由表 + 邻居发现；「ID 小的让」→ TCP 同时打开的冲突处理。每一行 1969 年的条款，都能在今天的协议栈里找到投胎后的位置。

三、亮点速览

  1. 同一主题两份文档的"并行发现"——RFC 1 和 2 独立写却结论一致，说明有些答案不依赖于个人，是问题本身逼出来的。
  2. 三种链路的分层——把"连接"从逻辑上彻底拆开，比 RFC 1 的"32 条平均主义"精确得多。
  3. 288 = lcm(24,32,36)——教科书级的异构互操作解法。
  4. 完整的错误路径——超时、panic、撞车仲裁，状态机全覆盖。RFC 1 说"这样挺好"，RFC 2 说"出错了你该怎么办"。
  5. Transparent I/O 的远见——"网络调试用的裸管道"，四十年后成为 raw socket 和 SDN 数据面的精神源头。

四、成败与后续

  • 活下来的：控制/主/辅三类链路的概念整合进了 NCP 协议（RFC 33 起，1970 年）；"像 TTY 一样登录远端"成为 telnet（RFC 15 提出）的直接蓝图；端到端顺序相关校验一路传到 TCP 的 checksum。
  • 被埋葬的：模拟电话线模式（一次一个字符）上线后立刻被真实带宽需求取代；8-bit 校验和太弱，后来换成了 16-bit；"Transparent I/O"在 NCP 时代没成为主流，raw socket 要等 BSD 才有。
  • 历史彩蛋：RFC 2 开头写着 [page 1 missing]——第一页丢了，所以这份文档从"1 LINKS"直接开始。1969 年的文档管理就是这么野：缺页、笔误（"elaspse"）、重复编号（14b3 出现两次）到处都是——但内容依然完整可读。这也是 RFC 文化的一部分：不完美也要发，发了再改。
