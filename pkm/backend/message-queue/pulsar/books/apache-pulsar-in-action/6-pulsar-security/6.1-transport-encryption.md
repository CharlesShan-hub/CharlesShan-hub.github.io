## 6.1 Transport encryption

By default, the data transmitted between a Pulsar broker and a Pulsar client is sent in plain text. This means any sensitive data contained within a message, such as passwords, credit card numbers, and social security numbers, is susceptible to being intercepted by eavesdroppers as it is transmitted over the network. Therefore, the first layer of defense is ensuring that the data transmitted between a Pulsar broker and a Pulsar client is encrypted *before* it is transmitted.

默认情况下，Pulsar broker 与 Pulsar client 之间传输的数据是明文发送的。这意味着消息中所含的任何敏感数据——例如密码、信用卡号和社会安全号码——在网络传输过程中都有可能被窃听者截获。因此，第一道防线就是确保 Pulsar broker 与 Pulsar client 之间传输的数据在被发送*之前*就已经加密。

Pulsar allows you to configure all communication to use transport layer security (TLS), which is a common cryptographic protocol that provides data encryption only as it is transported across the network. This is why it is often referred to as encryption for “data in motion”—the data is decrypted on the receiving end and therefore no longer encrypted once it reaches its destination.

Pulsar 允许你把所有通信配置为使用传输层安全性协议（TLS），这是一种常见的加密协议，它只在数据跨越网络传输的那一刻提供加密。正因如此，它常被称为“动态数据”（data in motion）加密——数据会在接收端被解密，因此一旦抵达目的地就不再处于加密状态。

Enabling TLS on Pulsar

在 Pulsar 上启用 TLS

Now that I have covered the basics of TLS wire encryption at a fairly high level, let’s focus on how we can use this technology to secure our communications between our Pulsar brokers and our clients. Since the Pulsar documentation does a fair job of outlining the steps required to enable TLS on Pulsar, I have decided that, rather than republish those same steps here, I will capture all of those steps in a single script that can be used to automate the process inside a Docker-based image.

至此我已经在相当高的层面上讲完了 TLS 链路加密的基本原理，接下来我们把注意力放到如何用这项技术保护 Pulsar broker 与客户端之间的通信。由于 Pulsar 官方文档已经把在 Pulsar 上启用 TLS 所需的步骤讲得相当清楚，我决定不在这里重复罗列同样的步骤，而是把所有这些步骤收录进一个脚本，用来在基于 Docker 的镜像中自动化完成整个过程。

I will then discuss the commands contained within the scripts in greater detail, as they relate to the discussion we had in the previous section, so you have a better understanding of why these steps are important and how you might modify them to suit your needs in a true production environment. If you look inside the GitHub repo (https://github.com/david-streamlio/pulsar-in-action) associated with this book, you will find a Dockerfile similar to the one shown in listing 6.1 under the docker-image/pulsar-standalone folder.

随后我会结合上一节的讨论，更详细地讲解脚本中包含的命令，让你更好地理解为什么这些步骤很重要，以及在真正的生产环境中该如何修改它们以满足自己的需要。如果你去查看与本书配套的 GitHub 仓库（https://github.com/david-streamlio/pulsar-in-action），会在 docker-image/pulsar-standalone 目录下找到一个与清单 6.1 所示类似的 Dockerfile。

For those of you unfamiliar with Docker, a Dockerfile is a simple text file that contains a series of instructions that are executed sequentially by the Docker client when creating an image. They can be thought of as recipes or blueprints for building Docker images and provide a simple way to automate the image-creation process. Now that we have a better understanding of Docker images, it is time to create our own. Our goal is to create an image that extends the capability of the pulsar-standalone image we used previously to include all of the security features I will be discussing throughout this chapter.

对于不熟悉 Docker 的读者，Dockerfile 就是一个简单的文本文件，其中包含一系列指令，Docker 客户端在创建镜像时会按顺序执行这些指令。可以把它们理解为构建 Docker 镜像的“菜谱”或“蓝图”，它们提供了一种把镜像创建过程自动化的简便方式。既然我们已经对 Docker 镜像有了更清楚的认识，那就来创建我们自己的镜像吧。我们的目标是创建一个镜像，在之前用过的 pulsar-standalone 镜像基础上扩展能力，把本章将要讨论的全部安全特性都包含进去。

I will start by specifying that I wish to use the non-secured apachxpulsar/pulsar-standalone:latest image as the base image by using the FROM keyword. For those of you familiar with object-oriented languages, this is effectively the same as inheriting from a base class. All of the base image’s services, features, and configurations are automatically included in our image, which ensures that our Docker images will also provide a complete Pulsar environment for testing purposes without having to replicate those commands in our Dockerfile.

我首先用 FROM 关键字声明：希望以未启用安全防护的 apachepulsar/pulsar-standalone:latest 镜像作为基础镜像。对于熟悉面向对象语言的读者来说，这实际上等同于从一个基类继承。基础镜像的全部服务、特性和配置都会被自动包含进我们的镜像，这就确保了我们的 Docker 镜像同样能提供一个完整的 Pulsar 测试环境，而不必在自己的 Dockerfile 里把那些命令再抄一遍。

After setting the PULSAR_HOME environment variable, I use the COPY keyword to replace both the Pulsar broker and client configuration files with ones that are properly configured to secure the Pulsar instance. This is an important step, as once a container based on this image is launched, it is impossible to change these settings and have them take effect. Next, we add the contents of the manning directory to the Docker image and run a command to enable execute permission on all of the bash scripts that were added in the previous command, so we can execute them.

设置完 PULSAR_HOME 环境变量之后，我用 COPY 关键字把 Pulsar broker 和客户端的配置文件都替换成已正确配置、可用于保护该 Pulsar 实例的版本。这是很关键的一步，因为一旦基于该镜像的容器启动，就无法再更改这些设置并使其生效了。接着，我们把 manning 目录的内容添加进 Docker 镜像，并运行一条命令为上一步添加进来的所有 bash 脚本开启可执行权限，这样我们后面才能执行它们。

At the end of the Dockerfile are a series of bash scripts that get executed in order to generate the necessary security credentials, certificates, and keys required to secure a Pulsar cluster. Let’s examine the first script, named enable-tls.sh, which performs all the steps necessary to enable TLS wire encryption on the Pulsar cluster.

Dockerfile 末尾是一系列 bash 脚本，它们会被依次执行，用以生成保护 Pulsar 集群所需的各种安全凭据、证书和密钥。我们先来看第一个脚本 enable-tls.sh，它完成了在 Pulsar 集群上启用 TLS 链路加密所需的全部步骤。

The pulsar-standalone Docker image includes OpenSSL, which is an open source library that provides several command-line tools for issuing and signing digital certificates. Since we are running in a development environment, we will use these tools to act as our own certificate authority to produce self-signed certificates rather than use an internationally trusted third-party certificate authority (CA) (e.g., VeriSign, DigiCert) to sign our certificates. In a production environment you should *always* rely on a third-party CA.

pulsar-standalone Docker 镜像中包含了 OpenSSL，这是一个开源库，提供若干用于签发和签署数字证书的命令行工具。由于我们运行在开发环境中，我们将用这些工具来充当自己的证书颁发机构，生成自签名证书，而不是去找国际公认的第三方证书颁发机构（CA）（例如 VeriSign、DigiCert）来签署证书。在生产环境中，你*始终*应当依赖第三方 CA。

Acting as a CA means dealing with cryptographic pairs of private keys and public certificates. The very first cryptographic pair we’ll create is the root pair. This consists of the root key (ca.key.pem) and root certificate (ca.cert.pem). This pair forms the identity of your CA. Let’s examine the first part of the enable-tls.sh script, which generate these. As we can see from the following listing, the first command in the script generates the root key, while the second command creates the public X.509 certificate using the root key that was generated in the previous step.

充当 CA 意味着要跟成对的私钥与公共证书打交道。我们要创建的第一个密钥对是根密钥对，它由根密钥（ca.key.pem）和根证书（ca.cert.pem）组成。这一对就构成了你的 CA 的身份。我们来看看 enable-tls.sh 脚本中生成它们的第一部分。从下面这份清单可以看到，脚本中的第一条命令生成根密钥，第二条命令则使用上一步生成的根密钥来创建公开的 X.509 证书。

Listing 6.2 Portion of enable-tls.sh that creates CA

```bash
#!/bin/bash

export CA_HOME=$(pwd)
export CA_PASSWORD=secret-password                                    ❶

mkdir certs crl newcerts private
chmod 700 private/
touch index.txt index.txt.attr
echo 1000 > serial

# Generate the certificate authority private key
openssl genrsa -aes256 \                                            ❷
   -passout pass:${CA_PASSWORD} \                                   ❸
   -out /pulsar/manning/security/cert-authority/private/ca.key.pem \
   4096                                                              ❹

# Restrict Access to the certificate authority private key   
chmod 400 /pulsar/manning/security/cert-authority/private/ca.key.pem ❺

# Create the X.509 certificate.
openssl req -config openssl.cnf \
  -key /pulsar/manning/security/cert-authority/private/ca.key.pem \   ❻
  -new -x509 \                                                        ❼
  -days 7300 \                                                        ❽
  -sha256 \
  -extensions v3_ca \
  -out /pulsar/manning/security/cert-authority/certs/ca.cert.pem \
  -subj '/C=US/ST=CA/L=Palo Alto/CN=gottaeat.com' \                   ❾
  -passin pass:${CA_PASSWORD}❿
```

❶ We use an environment variable to set the password for the CA root key.

❶ 我们用一个环境变量来设置 CA 根密钥的密码。

❷ Encrypt the root key with AES 256-bit encryption.

❷ 用 AES 256 位加密来保护根密钥。

❸ Generates the private key that is secured with a strong password

❸ 生成用强密码保护的私钥。

❹ Use 4096 bits for the root key.

❹ 根密钥使用 4096 位。

❺ Anyone in possession of the root key and password can issue trusted certificates.

❺ 任何同时掌握根密钥和密码的人都能签发受信任的证书。

❻ Generates the root certificate using the root key

❻ 使用根密钥生成根证书。

❼ Requests a new X.509 certificate

❼ 申请一张新的 X.509 证书。

❽ Give the root certificate a long expiry date.

❽ 给根证书设置一个较长的有效期。

❾ Specify the organization for which the certificate is valid.

❾ 指定该证书所适用的组织。

❿ Allows us to provide the password for the root key from the command line without a prompt

❿ 让我们可以在命令行直接提供根密钥的密码，而不必等待交互式提示。

At this point the script has generated a password-protected private key (ca.key.pem) and root certificate (ca.cert.pem) for our internal CA. The script purposely generates the root certificate to a known location, so we can refer to it from inside the broker’s configuration file, /pulsar/conf/standalone.conf. Specifically, we have preconfigured the tlsTrustCertsFilePath property to point to the location where the root certificate was generated. In a production environment where you are using a third-party CA, you will be provided with a certificate that can be used to authenticate the X.509 certificates and update the property to point to that certificate instead.

到这里，脚本已经为我们的内部 CA 生成了受密码保护的私钥（ca.key.pem）和根证书（ca.cert.pem）。脚本特意把根证书生成到一个已知位置，这样我们就能在 broker 的配置文件 /pulsar/conf/standalone.conf 中引用它。具体来说，我们已经预先把 tlsTrustCertsFilePath 属性配置为指向根证书生成的位置。在使用第三方 CA 的生产环境中，对方会提供一份可用于验证 X.509 证书的证书，届时你需要更新该属性，改为指向那份证书。

Now that we have created a CA certificate, the next step is to generate a certificate for the Pulsar broker and sign it with our internal CA. When using a third-party CA, you would issue this request to them and wait for them to send you a certificate; however, since we are acting as our own certificate authority, we can issue the certificate ourselves, as shown in the following listing.

既然 CA 证书已经创建好了，下一步就是为 Pulsar broker 生成一张证书，并用我们的内部 CA 为它签名。使用第三方 CA 时，你需要把申请提交给他们，然后等他们把证书发回来；不过，由于我们现在自己就是证书颁发机构，所以可以直接把证书签出来，如下面清单所示。

Listing 6.3 Portion of enable-tls.sh that generates the Pulsar broker certificate

```bash
export BROKER_PASSWORD=my-secret                                      ❶

# Generate the Server Certificate private key
openssl genrsa -passout pass:${BROKER_PASSWORD} \                   ❷
      -out /pulsar/manning/security/cert-authority/broker.key.pem \
      2048                                                           ❸

# Convert the key to PEM format
openssl pkcs8 -topk8 -inform PEM -outform PEM \                      ❹
      -in /pulsar/manning/security/cert-authority/broker.key.pem \
      -out /pulsar/manning/security/cert-authority/broker.key-pk8.pem \
      -nocrypt

# Generate the server certificate request       
openssl req -config /pulsar/manning/security/cert-authority/openssl.cnf \
      -new -sha256 \
      -key /pulsar/manning/security/cert-authority/broker.key.pem \
      -out /pulsar/manning/security/cert-authority/broker.csr.pem \
      -subj '/C=US/ST=CA/L=Palo Alto/O=IT/CN=pulsar.gottaeat.com' \  ❺
      -passin pass:${BROKER_PASSWORD}                                ❻

# Sign the server certificate with the CA
openssl ca -config /pulsar/manning/security/cert-authority/openssl.cnf \
      -extensions server_cert \                                      ❼
      -days 1000 -notext -md sha256 -batch \                         ❽
      -in /pulsar/manning/security/cert-authority/broker.csr.pem \
      -out /pulsar/manning/security/cert-authority/broker.cert.pem \
      -passin pass:${CA_PASSWORD}                                     ❾
```

❶ We use an environment variable to set the password for the server certificate’s private key.

❶ 我们用一个环境变量来设置服务器证书私钥的密码。

❷ Generates the private key that is secured with a strong password

❷ 生成用强密码保护的私钥。

❸ Use 2048 bits for the private key.

❸ 私钥使用 2048 位。

❹ The broker expects the key to be in PKCS 8 format.

❹ broker 要求密钥采用 PKCS 8 格式。

❺ Specify the organization and hostname for which the certificate is valid.

❺ 指定该证书所适用的组织与主机名。

❻ Allows us to provide the password for the key from the command line without a prompt

❻ 让我们可以在命令行直接提供该密钥的密码，而不必等待交互式提示。

❼ Specify that this certificate is intended to be used by a server.

❼ 声明该证书供服务器端使用。

❽ Give the server certificate a long expiry date.

❽ 给服务器证书设置一个较长的有效期。

❾ We need to provide the password for the CA’s private key, since we are acting as the CA.

❾ 由于我们自己充当 CA，所以需要提供 CA 私钥的密码。

At this point you have a broker certificate (broker.cert.pem) and its associated private key (broker.key-pk8.pem) that you can use along with ca.cert.pem to configure TLS transport encryption for your broker and proxy nodes. Again, the script purposely generates the broker certificate to a known location, so we can refer to it from inside the broker’s configuration file, /pulsar/conf/standalone.conf. Let’s take a look at all the properties that were changed to enable TLS for Pulsar.

到这里，你已经拿到了 broker 证书（broker.cert.pem）及其对应的私钥（broker.key-pk8.pem），可以配合 ca.cert.pem 一起，为你的 broker 和 proxy 节点配置 TLS 传输加密。同样地，脚本特意把 broker 证书生成到一个已知位置，以便我们能在 broker 的配置文件 /pulsar/conf/standalone.conf 中引用它。下面我们来看看为了在 Pulsar 上启用 TLS 而改动的所有属性。

Listing 6.4 TLS property changes to the standalone.conf file

```properties
#### To Enable TLS wire encryption #####
tlsEnabled=true
brokerServicePortTls=6651
webServicePortTls=8443

# The Broker certificate and associated private key
tlsCertificateFilePath=/pulsar/manning/security/cert-authority/broker.cert.pem
tlsKeyFilePath=//pulsar/manning/security/cert-authority/broker.key-pk8.pem

# The CA certificate
tlsTrustCertsFilePath=/pulsar/manning/security/cert-authority/certs/ca.cert.pem

# Used for TLS negotiation to specify which ciphers we consider safe.
tlsProtocols=TLSv1.2,TLSv1.1
tlsCiphers=TLS_DH_RSA_WITH_AES_256_GCM_SHA384,TLS_DH_RSA_WITH_AES_256_CBC_SHA
```

    }
}

That concludes the configuration of TLS wire encryption on the Pulsar broker. From this point forward, all communication with the broker will be over SSL, and all traffic will be encrypted to prevent unauthorized access to the data contained inside the messages that are published to and consumed from the Pulsar broker. You can experiment some more with this container, but once you are finished, you should be sure to run docker stop pulsar && docker rm pulsar to stop the container and remove it. Both of these steps are necessary to rebuild the Docker image in the next section to enable support for authentication in the pulsar-standalone image.
