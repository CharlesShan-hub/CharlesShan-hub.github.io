# 7.3.4 Complete example
Now that we have walked through the code inside each of the Maven modules, it is time to walk through an end-to-end demonstration of the interaction between the CustomerSimulatorSource and the OrderValidationService. It is important to note that, for this first demonstration, both of these classes will be using the exact same version of the schema (e.g., the domain-schema-0.0.1.jar). Consequently, both the producer’s and consumer’s schemas will be compatible with one another.

既然我们已经逐个看过了每个 Maven 模块中的代码，现在是时候走一遍端到端的演示，看看 CustomerSimulatorSource 与 OrderValidationService 之间是如何交互的了。有一点很重要，需要说明：在这第一个演示中，这两个类使用的将是完全相同的 schema 版本（即 domain-schema-0.0.1.jar）。因此，生产者和消费者的 schema 彼此之间必然是兼容的。

First, we need to have a running instance of the pia/pulsar-standalone-secure Docker image to serve as the Pulsar cluster we will use for testing. Therefore, you will need to execute the commands shown in the following listing to start an instance (if you don’t already have one running), publish the security credentials needed by both of the LocalRunner instances, and create the topics that will be used.

首先，我们需要有一个正在运行的 pia/pulsar-standalone-secure Docker 镜像实例，作为我们将用于测试的 Pulsar 集群。因此，你需要执行下面清单中所示的命令，来启动一个实例（如果你还没有在运行一个的话）、发布两个 LocalRunner 实例所需的安全凭据，并创建将要使用的那些主题。

Listing 7.10 Preparing the Pulsar cluster

```bash
$ docker run -id --name pulsar --hostname pulsar.gottaeat.com -p:6651:6651 \
  -p 8443:8443 -p 80:80 --volume=${HOME}/exchange:/pulsar/manning/dropbox \
  -t pia/pulsar-standalone-secure:latest                                    ❶

$ docker exec -it pulsar bash                                               ❷

root@pulsar:/# /pulsar/manning/security/publish-credentials.sh              ❸
root@pulsar:/# /pulsar/bin/pulsar-admin tenants create orders               ❹
root@pulsar:/# /pulsar/bin/pulsar-admin namespaces create orders/inbound    
root@pulsar:/# /pulsar/bin/pulsar-client consume -n 0 -s my-sub \
  persistent://orders/inbound/food-orders                                   ❺
```

❶ Launches the Pulsar standalone image, and maps a volume for sharing the security credentials

❶ 启动 Pulsar 独立模式镜像，并挂载一个卷用于共享安全凭据。

❷ SSH into the Docker container you just launched.

❷ SSH 进入你刚启动的那个 Docker 容器。

❸ Publish all of the security credentials to the ${HOME}/exchange directory on your local machine.

❸ 把所有安全凭据发布到本机上的 ${HOME}/exchange 目录。

❹ Create the tenant and namespace we are going to use.

❹ 创建我们将要使用的租户和命名空间。

❺ Start a consumer on the specified topic.

❺ 在指定主题上启动一个消费者。

The last line in listing 7.10 starts a consumer on the topic containing the FoodOrder events generated by the CustomerSimulatorSource. This will automatically create the topic and allow us to confirm that the messages are getting published. Leave this command shell open so we can monitor the messages as they come in, and switch to your local IDE that you are using to review the code from the GitHub project associated with this chapter of the book. Navigate to the customer-mobile-app-simulator module, and run the CustomerSimulatorSource as a Java application, which will execute the LocalRunner code shown in listing 7.7.

清单 7.10 中的最后一行，在包含由 CustomerSimulatorSource 所生成 FoodOrder 事件的那个主题上启动了一个消费者。这会自动创建该主题，并让我们能够确认消息确实被发布出来了。请让这个命令行窗口保持打开，以便我们监视陆续进来的消息，然后切换到你本地那个用来审阅本书本章配套 GitHub 项目代码的 IDE。导航到 customer-mobile-app-simulator 模块，把 CustomerSimulatorSource 当作一个 Java 应用运行起来，这将执行清单 7.7 中所示的 LocalRunner 代码。

If everything goes as expected, you should start seeing Avro messages appear in the command shell window as the messages are getting delivered to the consumer. 如果一切顺利，随着消息被投递给消费者，你应该会开始看到 Avro 消息出现在那个命令行窗口中。当你看到下面这段预期输出示例时，会发现其中的载荷是可读文本与二进制数据的混合体：

This is because the consumer we launched from the command line does not have a schema associated with it. Consequently, the raw bytes of the message, which in this case are encoded in Avro’s binary format, are not deserialized before being delivered to the consumer and are treated as raw bytes instead. This should give insight into the actual content of the messages that are being transmitted from producer to consumer.

这是因为我们从命令行启动的那个消费者并没有关联任何 schema。因此，消息的原始字节（在本例中是以 Avro 二进制格式编码的）在被投递给消费者之前没有经过反序列化，而是被当作原始字节来处理。这应该能让你对生产者与消费者之间实际传输的消息内容有所了解。

Next, let’s switch back to your IDE, navigate to the order-validation-service module and run the OrderValidationService as a Java application, which will execute the LocalRunner code shown in listing 7.9 to start the consumer. You should see messages printed to stdout that contain food order data, but in JSON format now instead of the Avro binary data we were seeing in the schema-less consumer window. This is because the function has a schema associated with it, which means the Pulsar framework is automatically serializing the raw message bytes into the appropriate Java class based on the Avro schema definition:

接下来，我们切回你的 IDE，导航到 order-validation-service 模块，把 OrderValidationService 当作一个 Java 应用运行起来——这将执行清单 7.9 中所示的 LocalRunner 代码来启动消费者。你应该会看到包含餐品订单数据的消息被打印到标准输出，只不过这次是 JSON 格式，而不是我们在那个无 schema 消费者窗口中所看到的 Avro 二进制数据。这是因为该函数关联了一个 schema，也就是说 Pulsar 框架会依据 Avro schema 定义，自动把原始消息字节序列化成恰当的 Java 类：

One of the best features of Avro that makes it a great solution for message-based microservice communication is its support for schema evolution. When a service that is writing messages updates its schema, the services consuming the messages can continue processing them without requiring any coding changes, provided that the producer’s new schema is compatible with the older version being used by the consumers.

Avro 之所以是基于消息的微服务通信的绝佳方案，其最好的特性之一就是它对 schema 演进的支持。当写入消息的那个服务更新了自己的 schema，消费这些消息的服务可以继续处理它们，无需做任何代码改动——前提是生产者的新 schema 与消费者正在使用的旧版本兼容。

Currently, both our producer and consumer are using the same version of the domain-schema JAR file (i.e. 0.0.1), and thus are also using the exact same schema version. While this is the expected behavior, it does not effectively demonstrate Pulsar’s schema evolution capabilities. I will demonstrate this capability in the next section by walking through the project code on the 0.0.2 branch of the associated GitHub project. Therefore, you will need to switch to the 0.0.2 branch before walking through the examples and, most importantly, leave your Docker container running as is.

目前，我们的生产者和消费者使用的是同一个版本的 domain-schema JAR 文件（即 0.0.1），因而也在使用完全相同的 schema 版本。虽然这是预期的行为，但它并不能有效地展示 Pulsar 的 schema 演进能力。我将在下一节中通过走读配套 GitHub 项目 0.0.2 分支上的项目代码来演示这一能力。因此，在开始走读这些示例之前，你需要先切换到 0.0.2 分支；而最重要的是，让你的 Docker 容器保持现状、继续运行。
