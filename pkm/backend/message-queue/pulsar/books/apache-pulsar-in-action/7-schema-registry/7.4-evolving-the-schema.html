7.4 Evolving the schema

2026-10-08book

During our weekly meeting with the customer mobile application team, we are informed that their initial testing has revealed a gap in their requirements. Specifically, the current food order schema does not support the ability for customers to customize their food orders to their particular tastes. Currently, a customer cannot specify that they want no onions on their hamburgers or extra guacamole on their burritos. Consequently, the schema will have to be revised, and an additional field named customizations will be added to the original menu item type, as shown in the following listing.

在与客户移动应用团队举行的周会上，我们得知他们前期的测试暴露出了需求上的一处缺口。具体来说，当前的餐品订单 schema 并不支持客户按个人口味定制餐品。目前，客户无法指定自己的汉堡要不加洋葱，或者墨西哥卷饼要多加牛油果酱。因此，这个 schema 必须修订，需要在原有的菜单项类型上增加一个名为 customizations 的字段，如下面清单所示。

Listing 7.11 Evolving the schema

@namespace("com.gottaeat.domain.resturant")

protocol ResturantsProtocol {

  record MenuItem {
    long item_id;
    string item_name;
    string item_description;
    array<string> customizations = [“”];      ❶
    float price;
  }
}

❶ The newly added field to support customizations of individual food items with a default value

❶ 新增加的字段，用于支持对单个餐品进行定制，并带有默认值。

After making this change to the schema inside the domain-schema module, you should also update the artifact version in the pom.xml file to 0.0.2 so we can differentiate between the two versions. Once these changes have been made to the source code, you should execute the command shown in the following listing to generate the Java classes’ source files, compile them, and jar them into the domain-schema-0.0.2.jar JAR file.

在 domain-schema 模块中改完这个 schema 之后，你还应该把 pom.xml 文件中的构件版本更新为 0.0.2，以便我们能区分这两个版本。源码改完以后，你需要执行下面清单中所示的命令，生成 Java 类的源文件、编译它们，并把它们打成 domain-schema-0.0.2.jar 这个 JAR 文件。

Listing 7.12 Generating the Java classes from the updated Avro schema

$ cd ./domain-schema
$ mvn install

Make sure that the version being built is 0.0.2. If you fail to update the version number in the pom.xml file and leave it as 0.0.1, you will overwrite the existing jar that has the old schema version in it, and your results will differ from the ones shown. If you happen to inadvertently overwrite the domain-schema-0.0.1.jar, you can remove the newly added field and rebuild the jar file. Then, add the field back, change the version number to 0.0.2, and rebuild it again. You can easily verify that the Java classes you generated were based on the new schema version by looking for the customizations field in the src/main/java/com/gottaeat/domain/restaurant/MenuItem.java class.

请务必确认正在构建的版本是 0.0.2。如果你忘了更新 pom.xml 中的版本号、让它继续留在 0.0.1，你就会覆盖掉那个包含旧 schema 版本的现有 jar，那么你的结果就会与这里所展示的不同。万一你不小心覆盖了 domain-schema-0.0.1.jar，可以把新加的字段去掉、重新构建一遍 jar 文件；然后再把字段加回来、把版本号改成 0.0.2、再重新构建一次。你可以很容易地验证自己生成的 Java 类确实是基于新的 schema 版本：只需在 src/main/java/com/gottaeat/domain/restaurant/MenuItem.java 这个类中查找 customizations 字段即可。

接下来，我会把 customer-mobile-app-simulator 模块中 domain-schema 依赖的版本号更新为使用更新后的 schema，如下面清单所示。

<dependency>

Since the 0.0.2 version of the schema is backward compatible with the 0.0.1 version used by the OrderValidationService, it will be able to consume the messages based on the newer schema version. As you can see from the deserialized Avro messages shown next, since these newer messages are being deserialized with the older schema, the newly added customizations field is ignored. It is also worth pointing out that no code changes were required to the OrderValidationService. Therefore, had this been a production environment, the currently running instance of the service could remain running without disruption even though the mobile application had made changes to its code base, making them completely decoupled from one another even when an API change (message format) is made.

还有一点值得一提：OrderValidationService 无需做任何代码改动。因此，假如这是一个生产环境，即便移动应用已经改了自己的代码库，当前正在运行的那个服务实例也可以不受干扰地继续运行——这使得双方即使在进行 API 变更（消息格式变更）时，也完全彼此解耦。
