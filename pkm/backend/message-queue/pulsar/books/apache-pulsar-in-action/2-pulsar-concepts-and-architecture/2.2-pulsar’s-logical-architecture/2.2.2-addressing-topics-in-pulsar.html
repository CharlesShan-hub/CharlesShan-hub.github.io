2.2.2 Addressing topics in Pulsar

2026-10-08book

The hierarchical structure of Pulsar’s logical layer is reflected in the naming convention of endpoints used to access topics within Pulsar. As you can see in figure 2.10, each topic addressed within Pulsar contains both the tenant and namespace to which it belongs. The address also contains a persistency prefix that indicates whether the message contents are persisted to long-term storage or they are only retained in the bookie’s memory space. If a topic name is created with a prefix of persistent://, then all messages that have been received but not yet acknowledged will be stored on multiple bookie nodes, and thus, can survive broker failures.

Pulsar 逻辑层的层级结构，反映在 Pulsar 内部用于访问主题的端点命名约定上。正如你在图 2.10 中看到的，在 Pulsar 中被寻址的每个主题都包含它所属的租户和命名空间。该地址还包含一个持久性前缀，用以表明消息内容是被持久化到长期存储，还是仅仅保留在 bookie 的内存空间中。如果一个主题名以 persistent:// 前缀创建，那么所有已收到但尚未被确认的消息都会被存储在多个 bookie 节点上，因而能够在 broker 故障中存活下来。

Pulsar also supports non-persistent topics, which retain all unacknowledged messages in the broker memory. Non-persistent topic names begin with the non-persistent:// prefix to indicate this behavior. When using non-persistent topics, brokers immediately deliver messages to all connected subscribers without persisting them.

Pulsar 还支持非持久化主题，它把所有未确认的消息保留在 broker 的内存中。非持久化主题的名称以 non-persistent:// 前缀开头，以表明这种行为。使用非持久化主题时，broker 会立即把消息投递给所有已连接的订阅者，而不对它们做持久化。

When using non-persistent delivery, any form of broker failure, or disconnecting a subscriber from a topic, results in all in-transit messages being lost on the (non-persistent) topic. This means that the topic subscribers will never be able to receive those messages even if they reconnect. While non-persistent messaging is usually faster than persistent messaging because it avoids the latency associated with persisting the data to disk, it is only advisable to use it if you are certain that your use case can tolerate the loss of messages.

使用非持久化投递时，任何形式的 broker 故障，或者把某个订阅者从主题上断开，都会导致该（非持久化）主题上所有在途消息丢失。这意味着该主题的订阅者即使重新连接，也永远无法再收到那些消息。虽然非持久化消息通常比持久化消息更快，因为它避免了把数据持久化到磁盘所带来的延迟，但只有在你确信自己的用例能够容忍消息丢失时，才建议使用它。
