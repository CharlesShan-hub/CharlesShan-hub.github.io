最后，每个集群还拥有自己的本地 ZooKeeper 集群，Pulsar 用它来存储租户、命名空间和主题等集群专属的配置信息，包括安全策略和数据保留策略。这是在我们前面讨论过的 managed ledger 信息之外的部分。

ZooKeeper basics

ZooKeeper 基础

According to the official Apache website, “ZooKeeper is a centralized service for maintaining configuration information, naming, providing distributed synchronization, and providing group services” (https://zookeeper.apache.org), which is an elaborate way of saying it is a distributed data source. ZooKeeper provides a decentralized location for storing information, which is crucial within distributed systems, such as Pulsar or BookKeeper.

根据 Apache 官方网站的说法，"ZooKeeper 是一项集中式服务，用于维护配置信息、命名、提供分布式同步以及提供组服务"（https://zookeeper.apache.org）——这是一种比较迂回的说法，实质上就是在说它是一个分布式数据源。ZooKeeper 提供了一个去中心化的信息存储位置，这在 Pulsar 或 BookKeeper 这样的分布式系统中至关重要。

Apache ZooKeeper solves the fundamental problem of achieving consensus (i.e., agreement) that virtually every distributed system must solve. Processes in a distributed system need to agree on several different pieces of information, such as the current configuration values and the owner of a topic. This is a problem particularly for distributed systems due the fact that there are multiple copies of the same component running concurrently with no real way to coordinate information between them. Traditional databases are not an option because they introduce a serialization point within the framework where all the calling services would be blocked waiting for the same lock on a table, which essentially eliminates all the benefits of distributed computing.

Apache ZooKeeper 解决了几乎每个分布式系统都必须解决的基础问题：如何达成共识（即一致性同意）。分布式系统中的各个进程需要对若干不同的信息达成一致，例如当前的配置值，以及某个主题的归属者。这对分布式系统而言尤其成问题，因为同一组件会有多个副本并发运行，而它们之间并没有真正有效的方式来协调信息。传统数据库不是一个可选项，因为它会在框架中引入一个串行化点：所有调用方服务都会被阻塞，等待同一张表上的同一把锁，这实际上抵消了分布式计算的所有好处。

Having access to a consensus implementation enables distributed systems to coordinate processes in a more effective manner by providing a compare-and-swap (CAS) operation to implement distributed locks. The CAS operation compares the value retrieved from ZooKeeper with an expected value and, only if they are the same, updates the value. This guarantees that the system is acting based on up-to-date information. One such example would be checking that the state of a BookKeeper ledger is open before writing any data to it. If some other process has closed the ledger, it would be reflected in the ZooKeeper data, and the process would know not to proceed with the write operation. Conversely, if a process were to close a ledger, this information would be sent to ZooKeeper so that it could be propagated to the other services, so they would know it is closed before they attempted to write to it.

有了共识实现可用，分布式系统就能通过提供比较并交换（compare-and-swap，CAS）操作来实现分布式锁，从而以更有效的方式协调各个进程。CAS 操作会把从 ZooKeeper 中取回的值与一个期望值进行比较，只有在两者相同时才更新该值。这保证了系统是基于最新信息来采取行动的。这样的一个例子是：在向 BookKeeper 的 ledger 写入任何数据之前，先检查它的状态是否为 open。如果某个其他进程已经关闭了该 ledger，这一点会反映在 ZooKeeper 的数据中，当前进程就会知道自己不应继续进行写入操作。反过来，如果某个进程要 close 一个 ledger，这一信息会被发送给 ZooKeeper，以便传播给其他服务，使它们在尝试写入之前就知道该 ledger 处于 closed 状态。

The ZooKeeper service itself exposes a file-system-like API so that clients can manipulate simple data files (znodes) to store information. Each of these znodes forms a hierarchical structure similar to a filesystem. In the following sections, I will examine the metadata that is retained within ZooKeeper along with how it is used and by whom so that you can see for yourself exactly why it is needed. The best way to do this is by using the zookeeper-shell tool that is distributed along with Pulsar, as shown in the following listing, to list all the znodes.

ZooKeeper 服务本身暴露了一个类文件系统的 API，使客户端能够操作简单的数据文件（znode）来存储信息。这些 znode 中的每一个都构成一个类似于文件系统的层级结构。在接下来的几节中，我将考察 ZooKeeper 中保存了哪些元数据、它们如何被使用以及被谁使用，以便你亲眼看出为什么需要它们。最好的方法是使用随 Pulsar 一起分发的 zookeeper-shell 工具来列出所有 znode，如下面的清单所示。

As you can see in listing 2.1, there are a total of 11 different znodes created inside ZooKeeper for Apache Pulsar and BookKeeper. These fall into one of four categories based on what information they contain and how it is used.

正如你在清单 2.1 中看到的，ZooKeeper 中为 Apache Pulsar 和 BookKeeper 创建了总共 11 个不同的 znode。按照它们所包含的信息以及使用方式，这些 znode 可分为四类。

Configuration data

配置数据

The first category of information is configuration data for tenants, namespaces, schemas, etc. All this information is slow-changing information that is only updated through the Pulsar administration API when a user creates or updates a new cluster, tenant, namespace, or schema and includes such things as security policies, message retention policies, replication policies, and schemas. This information is stored in the following znodes: /admin and /schemas.

第一类信息是租户、命名空间、schema 等的配置数据。所有这些信息都是缓慢变化的信息，只有在用户通过 Pulsar 管理 API 创建或更新新的集群、租户、命名空间或 schema 时才会被更新，其中包括安全策略、消息保留策略、复制策略和 schema 等内容。这些信息存储在以下 znode 中：/admin 和 /schemas。

Metadata storage

元数据存储

The managed ledger information for all of the topics is stored in the /managed-ledgers znode, while the /ledgers znode is used by BookKeeper to keep track of all the ledgers currently stored across all the bookies within the cluster.

所有主题的 managed ledger 信息存储在 /managed-ledgers 这个 znode 中，而 /ledgers 这个 znode 则由 BookKeeper 用来跟踪当前存放在集群内所有 bookie 上的全部 ledger。

正如你在清单 2.2 中看到的，还有一个名为 pulsar-managed-ledger-admin 的工具，它可以让你轻松访问 Pulsar 用来在 BookKeeper 中读写数据的 managed ledger 信息。在本例中，该主题的数据存放在两个不同的 ledger 上：ledgerID-20，它已关闭并包含 50,000 条 entry；以及 ledgerID-245，它当前处于打开状态，传入的数据将被发布到这里。

Dynamic coordination between services

服务之间的动态协调

The remaining znodes are all used for distributed coordination across the systems, including /bookies, which maintains a list of the bookies registered with the BookKeeper cluster, and /namespace, which is used by the proxy service to determine which broker owns a given topic. As we can see in the following listing, the /namespace znode hierarchy is used to store the bundle IDs for each namespace.

其余的 znode 都用于跨系统的分布式协调，其中包括 /bookies——它维护着已注册到 BookKeeper 集群中的 bookie 列表；以及 /namespace——proxy 服务用它来判断哪个 broker 拥有某个给定的主题。正如我们在下面的清单中看到的，/namespace 这个 znode 的层级结构被用来存储每个命名空间的 bundle ID。

As you’ll recall from our earlier discussion, the topic name is hashed by the proxy to determine the bundle name, which in this case is 0x40000000_0x80000000. The proxy then queries the /namespace/{tenant}/{namespace}/{bundle-id} znode to retrieve the URL for the broker that “owns” the topic.

正如你从我们前面的讨论中所记得的，proxy 会对主题名进行哈希以确定 bundle 名，在本例中是 0x40000000_0x80000000。随后 proxy 会查询 /namespace/{tenant}/{namespace}/{bundle-id} 这个 znode，以取得"拥有"该主题的 broker 的 URL。

Hopefully, this gives you some more insight into the role ZooKeeper plays inside a Pulsar cluster and how it provides a service that can be easily accessed by nodes that have been dynamically added to the cluster, so they can quickly determine the cluster configuration and start handling client requests. One such example would be the ability of newly added brokers to start serving data from a topic by referencing the data in the /managed-ledgers znode.

希望这能让你更深入地了解 ZooKeeper 在 Pulsar 集群中所扮演的角色，以及它如何提供一种可被动态加入集群的节点轻松访问的服务，使这些节点能够快速确定集群配置并开始处理客户端请求。其中一个例子就是：新加入的 broker 可以通过引用 /managed-ledgers 这个 znode 中的数据，开始为某个主题提供数据服务。
