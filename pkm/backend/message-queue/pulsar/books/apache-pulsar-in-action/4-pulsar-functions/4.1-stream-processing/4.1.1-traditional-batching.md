### 4.1.1 Traditional batching

Historically, the vast majority of data processing frameworks have been designed for batch processing. Traditional data warehouses, Hadoop, and Spark are just a few common examples of systems that process large datasets in batches. Data is often fed into these systems via long-running and complex ETL pipelines that cleanse, prepare, and format the incoming data for consumption. Messaging systems often serve as little more than intermediate buffers that store and route the data between the various processing stages of the pipeline.

从历史上看，绝大多数数据处理框架都是为批处理而设计的。传统数据仓库、Hadoop 和 Spark 只是几个常见的例子，它们都以批的方式处理大规模数据集。数据通常是通过长时间运行且复杂的 ETL 管道被送入这些系统的，这些管道会对传入的数据进行清洗、准备和格式化，以供消费。消息系统在这些管道中所起的作用，往往不过是介于各个处理阶段之间、用于存储和路由数据的中间缓冲区。

These long-running data ingestion pipelines were often implemented using stream processing engines, such as Apache Spark or Flink, that were designed to process large datasets efficiently by performing the processing in parallel. Newly arriving data elements were collected and then processed together at some point in the future as a batch. To maximize the throughput of these frameworks, the accumulation would take place over very large time intervals (hours) or until a certain amount of data (10s GBs) had been collected, which introduced an artificial delay in the data processing pipeline.

这些长时间运行的数据摄取管道，通常是使用 Apache Spark 或 Flink 这类流处理引擎来实现的——它们被设计为通过并行执行处理来高效地处理大规模数据集。新到达的数据元素会被收集起来，然后在未来的某个时间点作为一个批次一起处理。为了让这些框架的吞吐量最大化，累积过程会跨越非常大的时间间隔（数小时），或者一直持续到收集了一定数量的数据（数十 GB）为止，这在数据处理管道中引入了一种人为的延迟。
